\section{Abstract}

\section{Introduction}
As global warming and climate change swing in an unpredictable direction nowadays, building predictive mathematical models forecasting such inconsistent evolutionary dynamics has been rendered more vital than ever. However, the accurate modeling of the population dynamics most of the time depends hugely on the spatial variation of each individual with various genotypes \cite{okamoto2018}. Additionally, understanding the genetic architectures of each individual in the population is essential \cite{okamoto2018}. Both of these two aspects can never be easily modeled with either Ordinary or Stochastic Differential Equations (ODE or SDE). Hence, sPEGG, abbreviating for \textbf{simulating Population Evolution on General Purpose Graphic Processing Unit}, was designed as a form of agent-based population simulation model to cover those aforementioned needs, where each individual in the population was considered an \enquote{agent} \cite{okamoto2018}.

sPEGG starts with a set of simulation parameters defined and set by programmers, and after a certain amount of time steps, it provides the population dynamic data specific to those defined parameters earlier \cite{okamoto2018}. Interestingly, in this Big Data world where the global wildlife and field ecological database is massively growing, there comes a compelling question of whether the evolutionary patterns in such data can be explained using sPEGG's architecture; and if so, we need to estimate its simulation parameters that will eventually reconstruct those similar patterns observed in real population data.

To estimate numerical input parameters to any procedure in order to minimize the difference between its predicted output and the truth (often referred to as \textbf{loss}), numerical optimization solvers are often employed, which guide each input parameter against its gradient (derivative) until the loss value gets stuck inside any minima. But approximating the gradient for one individual parameter at a time is considered inefficient for a big estimation project that involves a gigantic amount of parameters \cite{thgaskin2023neural}, for two reasons: (1) We should use GPU to parallelize differentiating all parameters, and (2) derivative approximation is never as exact as the auto-differentiation functionality provided by multiple Python machine learning frameworks, such as \textbf{PyTorch} \cite{paszke2017automatic}. Thanks to its primary support of Neural Network engineering, PyTorch also comes with GPU parallelizing backend and auto-gradient feature \cite{paszke2017automatic}, enforcing the accuracy of gradient calculation.

Given that opportunity, we essentially asked ourselves if it would be feasible to incorporate sPEGG simulation model as a layer in any neural network architecture, and if so, to what extent that such a neural network could capture evolutionary dynamic patterns in the provided training data.

\section{Objectives}

In this study, we aimed to build a neural network pipeline incorporating two different sPEGG simulation models, one whose all genes contributed equally to the reproductive potential, another whose some genes contributed more to reproduction than other genes. To start easy, we only set 3 parameters, consisting of the recombination rates of both 3 loci in the model set up, to be all simulation parameters and explore their effects onto the genotypes that control the reproductive potential. We used the pre-implemented \textbf{NeuralABM} infrastructure to automate the workflow at ease, from sequencing population data and preparing for training dataset, to training a neural network and drawing its diagnostic plots \cite{thgaskin2023neural}. NeuralABM also makes parameter inputting (both Data Generation, ABM, and Neural Network parameters) more convenient. There is a note here, though, is that NeuralABM only supplies an infrastructure to automate the Neural Net training process, but does not provide users with a Neural Network model, which means users have to use PyTorch to build their desired Neural Network architecture, although it does provide the implementation of a very simple feed-forward network model \cite{thgaskin2023neural}.

\section{Methodology}
\subsection{Population Data Availability}

Due to the time constraint of the coursework (4-5 months), we were not able to find and process such real-life population data. Instead, we took the first 200 base pairs of the ecoli genome, provided by \textbf{snpArcher} \cite{snparcher2024}, as our reference genome, represented as a \textbf{fasta} file. We then had a Python script simulate the genetic variability in the population by augmenting the original reference genome, as seen in appendix \ref{app:code}. Specifically, the original sequence was copied all over to 20 individuals in the population, but there would be randomly determined mutations at some or all of these three locus positions, 10, 50, and 100. Such a procedure was repeated 10 times since we wanted to simulate across 10 time steps. Finishing such a long process, we obtained sequence data (fasta files) for all individuals at all time steps, each with a different genetic variation.

However, snpArcher compares sequence reads, not the whole genome data, against the reference genome to finally produce a Variant-Call File summarizing genetic variation \cite{snparcher2024}. Thus, we need to obtain sequence reads, represented as \textbf{fastq} files, of all individuals in the population across all time steps. Again, with simulated field data, we were not capable of using the sequencing technology in the lab to generate fastq files, so we had to simulate the reads from each individual's genome fasta file using a software called \textbf{ART 454} \cite{art454_2012}. Such a software can simulate a sequencing error profile representing a real sequencing technology \cite{art454_2012}.

Once a set of sequencing reads for the population across time was obtained, snpArcher was used to compare the individual reads to the reference genome and produce Variant-Call Files, since summarizing the genetic variability information requires multiple steps, all of which should be both handled by snpArcher \cite{snparcher2024}. This tool requires two other configuration files in addition to the reference genome's fasta and individual read fastq's, one of which is snpArcher parameters' configuration and another is the sample sheet, where each row contains two fastq files from a double pair-end read of an individual. These two configuration files were generated by a Python script, annotated in appendix \ref{app:code}. Downstream, the resulting Variant-Call Files were then processed by \textbf{vcftools}, which directly computed the allele frequency using the genetic variability summary presented in the VCFs \cite{vcftools2011}. Parts of these allele frequency data would be manipulated as our Training Dataset for the Neural Network pipeline.

\subsection{Training Data Generation}

Once our population dynamic data were generated and sequenced, for each simulation time step, we had one VCF file cover genetic variability of the entire population; in this case, we decided to entail 10 time steps. We then fed those 10 VCF files, one at a time, into the \textbf{vcftools} to have it output the population allele frequency at a time step, which was used to make one \enquote{row} in the training dataset. Since earlier on we mentioned that the script simulating genome data for each individual considered mutations at at most 3 loci, there should be at most 3 rows in the vcftools's output. However, only the frequency at one locus was favored within the training data, so we had a workflow configuration variable cover which locus to be examined (appendix \ref{app:code}). That same locus was being tracked across all 10 time steps, so there were 10 rows in the training dataset, each with the allele frequency at locus specified in the configuration file at a specific time step.

\subsection{sPEGG Simulation Model Architectures}

In order to construct our population simulation models, the sPEGG codebase was imported. Such a codebase implemented fundamental population movements such as reproduction, deaths, and even lower-order movements such as fertilization, mutations, and recombinations \cite{okamoto2018}. The performance of any models built upon sPEGG codebase is enhanced by manipulating the parallelizing advantage of GPUs using \textbf{CUDA} library, a branch of \textbf{C++} language \cite{cuda2008}.

To fit into the time frame of the coursework and also keep the pipeline implementation simple, we decided to use the very basic design of a simulation model from sPEGG described in section 2.2 of the article \cite{okamoto2018} or in the \texttt{Tutorial\_Simulation} example in the sPEGG codebase (appendix \ref{app:code}). \emph{We aimed to study different convergences of two versions of the sPEGG simulation model: (1) each gene contributes equally to the reproductive advantage, (2) one gene contributes more to such than others}. Therefore, one key difference in the implementation of these two versions lies in the genotype-phenotype mapping between a genotype and the reproduction-determinant phenotype (algorithms \ref{norepro} and \ref{repro}).

\begin{algorithm}[H]
\caption{sPEGG simulation model with all genes playing the equal roles in reproduction. In this procedure shown, two loci contribute equally to the reproduction phenotype.} \label{norepro}
\begin{algorithmic}[1]
    \Function{mapGenotypeToPhenotype}{momLocus1, dadLocus1, momLocus2, dadLocus2, coefsList}
        \State constant = coefsList[1]
        \State locus1Coef = coefsList[2]
        \State locus2Coef = coefsList[3]
        \State fecundity = constant + locus1Coef $\cdot0.5\cdot$ (momLocus1 + dadLocus1) + locus2Coef $\cdot0.5\cdot$ (momLocus2 + dadLocus2)
        \State \Return fecundity
    \EndFunction
\end{algorithmic}
\vspace{0.6em}
\end{algorithm}

\begin{algorithm}[H]
    \caption{sPEGG simulation model with genes playing unequal roles in reproduction. In this procedure shown, locus one influences fecundity 4 times stronger than locus 2.} \label{repro}
    \begin{algorithmic}[1]
        \Function{mapGenotypeToPhenotype}{momLocus1, dadLocus1, momLocus2, dadLocus2, coefsList}
            \State constant = coefsList[1]
            \State locus1Coef = coefsList[2]
            \State locus2Coef = coefsList[3]
            \State fecundity = constant + locus1Coef $\cdot0.5\cdot4\cdot$ (momLocus1 + dadLocus1) + locus2Coef $\cdot0.5\cdot$ (momLocus2 + dadLocus2)
            \State \Return fecundity
        \EndFunction
    \end{algorithmic}
    \vspace{0.6em}
\end{algorithm}

We hypothesized that the Neural Network having the first sPEGG model would not converge well, while the one with differential reproductive genetic influences should somewhat converge in terms of the parameter(s) driving the evolution of the genotype (or locus) that had the strongest influence on the fecundity. In this case, both of these two models had three simulation parameters, which were the \emph{recombination rates for both three loci}. The implementation of both these two models can be found in appendix \ref{app:code}.

The challenge emerged when the simulation models were written in C, but the overall NeuralABM pipeline and PyTorch Neural Network model were supposed to be in Python. In addressing it, we linked the object code of the simulation models directly with the Python code via \textbf{Pybind11}, which allowed us to call a C function directly in Python code as if it were a Python function \cite{pybind11}. That way, we could easily transfer the simulation parameters from our overall Python pipeline to C-implemented simulation models, then such models would transfer the simulated population output back to the earlier Python pipeline once the simulation finished. The github branch of the sPEGG codebase version that does support the pybind11 linker can be seen in appendix \ref{app:code}.

\subsection{Neural Network Architecture}

Again, for simplicity, we decided to start out with a simple feed-forward neural network architecture that receives an input of size corresponding to the size of the training dataset, and has three hidden nodes, so that the only layer inside of such a network would immediately produce a vector of only three elements, which were finally used as three simulation parameters, as in figure \ref{fig:nn}. Given the complete elimination of the normalized complexity of a typical neural network (most networks have multiple layers) and any further hidden nodes beyond the required amount to be able to get to the output size (in this case, 3), the job for our neural network was merely a numerical optimization task. The reason for this over-simplification was because of the inherent gradient vanishing problem \cite{gradientvanishing2013}, often happening when applying the chain rule across a very sophisticated network, and it would be better to just start out simple when we had not yet taken into account any probable inconsistency of the simulation models. That way, we could lay out a solid foundation, upon which we would, in the future, build more complicated but predictive architectures.

        \node[draw, circle, text width=4cm, align=center] (A) at (0,0) {N timestep population data};
        \node[draw, circle] (B) at (6,0) {Layer 1 (N, 3)};
        \node[draw, circle, text width=4cm, align=center] (C) at (12, 0) {Output 3 simulation parameters};
        \draw[->] (A) -- (B);
        \draw[->] (B) -- (C);
    \end{tikzpicture}
    \caption{Neural Network Architecture. Here we completely reduced the complexity of a typical neural network to account for any potential inconsistency in our simulation models}
    \label{fig:nn}
\end{figure}

Every neural network model must own a loss function that compute the \enquote{error} in its current prediction, from which it can learn and attempt to minimize. Once our neural network architecture outputs the three numbers supposed to be simulation parameters, they would be passed as arguments into a loss function, inside which a sPEGG simulation model would use them to reconstruct the population genetic data, and a Mean-Squared Error function would compute the difference between the training dataset and such simulated population data. Such a difference would be the final loss value for our neural network architecture. Described in algorithm \ref{alg:loss} is the procedure of such a loss function.

\begin{algorithm}
    \begin{algorithmic}[1]
        \Function{loss}{loc1RecomRate, loc2RecomRate, loc3RecomRate, trainingData}
            \State simulatedPop = \Call{spegg}{loc1RecomRate, loc2RecomRate, loc3RecomRate}
            \State diff = \Call{MSE}{simulatedPop, trainingData}
            \State \Return diff
        \EndFunction
    \end{algorithmic}
    \vspace{0.6em}
    \caption{Loss function. First, it has predicted parameters from the neural net fed into sPEGG to simulate a population data. Then, such simulated data are compared against the training data using an MSE function.}
    \label{alg:loss}
\end{algorithm}

\section{Result}
\subsection{Platform Incompatibility}

With the integration of sPEGG into the overall neural network architecture, we had believed that it would have smoothly auto-differentiated the three parameters (recombination rates of 3 loci) in parallel, until we discovered that every component of the neural network had to be programmed in PyTorch to be able to benefit from its auto-differentiation feature \cite{paszke2017automatic}. Here, our sPEGG models were both crafted even in another language, so when applying the chain rule, the gradient kept back-propagating until it encountered sPEGG, which was when the \enquote{computational graph} got disconnected \cite{paszke2017automatic}. That is because PyTorch \enquote{did not know} how to differentiate a numerical function programmed using an entire other platform, so the chain rule was unfortunately halted there.

So what was the workaround? Although Neural Network engineering with Pytorch requires every process and layer to be entirely written in terms of PyTorch tensors and operations, but it does provide a \enquote{wrapper} for non-PyTorch-native components. Here is how it functions:

\begin{figure}[H]
\begin{lstlisting}
    class Loss(torch.autograd.Function):
        @staticmethod
        def forward(threeRecomRates, trainingData):
            """
            This function calculates loss!
            """
            simulatedData = sPEGG(threeRecomRates)
            loss = MSE(simulatedData, trainingData)
            return loss
        
        @staticmethod
        def backward(currentThreeRecomRates, downstreamGradients):
            """
            This function helps calculate derivatives!
            """
            gradientThreeRecomRates = [0, 0, 0]
            for i in range(0, 3):
                currentParam = currentThreeRecomRates
                h = 0.01
                y = MSE(sPEGG(currentThreeRecomRates), trainingData)
                yh = MSE(sPEGG(currentThreeRecomRates[(i) += h]), trainingData)
                
                # one at a time, compute the gradient of each parameter
                gradientThreeRecomRates[i] = (y - yh) / h
            return gradientThreeRecomRates

\end{lstlisting}
\end{figure}

This essentially wraps sPEGG around PyTorch, which allows PyTorch to be able to compute sPEGG's gradients and seamlessly backpropagate. However, this workaround \textbf{approximates}, but does not \textbf{auto-differentiate}, each parameter's gradient, leading to an approximation error. Moreover, the above script only computes the derivative for one parameter at a time, so we did not really leverage the parallelizing advantage of PyTorch auto-differentiation feature here. Because of this platform incompatibility, our neural network was only performing as much as a regular numerical optimization function such as \texttt{optim()} in R \cite{r2024}, or \texttt{scipy.optimize.minimize()} in Python \cite{scipy2020}.

\subsection{Roles of the Fecundity-Controlling Genotype}

Contradicting to our hypothesis, the training loss for the model without any dinstinct fecundity-enhancing genotype showed a more consistently decreasing loss progression (figure \ref{fig:nogendiffloss}), while the one with loci 1 distinctly enhancing fecundity showed a more erratic yet still decreasing loss (figure \ref{fig:gendiffloss}).

The progression of three parameters (recombination rates of both 3 loci) was also distinct between two models. For the model without a specific fecundity genotype, genotype 1 recombination rate smoothly converged to near 0, while that of the other two genotypes smoothly converged to 1 (figure \ref{fig:nogendiffpred}). Conversely, for the other model with genotype 1 enhancing fecundity, the parameter convergences were a bit bumpier and eventually landed somewhere between 0 and 1, but never on those two bounds (figure \ref{fig:gendiffpred}). This suggests that with a fecundity-enhancing genotype, the overall evolutionary picture experiences a \enquote{tug-of-war} between the interwoven effects of both mortality-controlling and fecundity-controlling genotypes.
